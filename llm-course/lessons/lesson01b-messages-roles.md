# 第 1 课补充：messages 三个角色（system / user / assistant）到底什么区别

> 一句话记住：**assistant 就是"模型自己说过的话"**。它和 user 的区别不在内容格式，
> 而在"谁说的"——模型读对话时是带着角色视角读的。

## 1. 三角色对比表

| 角色 | 谁说的话 | 干什么用 | Java 类比 |
|---|---|---|---|
| `system` | 程序员（你）写给模型的总纲 | 定身份、定规则、定输出格式，全程生效 | application.yml 全局配置 / 请求头 |
| `user` | 终端用户的输入 | 提问、下达任务 | 请求参数 |
| `assistant` | **模型自己**之前的回复 | 让模型"记得自己说过什么"，或伪造示范 | 上次接口的返回值回填 |

## 2. 为什么需要 assistant 角色：API 是无状态的

大模型 API **没有会话记忆**。你以为的连续聊天，实际是每次调用都把完整历史重新发一遍：

```
第 1 次请求:  [system, user:A]           → 返回 answer1
第 2 次请求:  [system, user:A, assistant:answer1, user:B]   → 返回 answer2
```

`assistant: answer1` 就是你手动把上一次的返回值塞回去的。**不塞会怎样**：模型根本不知道之前聊过什么，第 2 句"继续"它就听不懂了。这就是第 1 课练习 3 要你亲手做的事。

类比：每次 HTTP 请求都带全量 ThreadLocal 会话快照，server 端什么都不存。

## 3. assistant 的三个实战用途

### 用途 ①：多轮对话（最基础）
把历史回复按顺序回填，上面第 2 次请求的例子就是。

### 用途 ②：伪造示范，稳定输出（第 2 课代码里在用）
```python
{"role": "user", "content": FEW_SHOT_EXAMPLE},
{"role": "assistant", "content": "明白了，我将严格按示例格式只返回 JSON 数组。"},
```
这条 assistant 消息**是假的**——模型根本没说过这句，是你在消息列表里手动编的。
效果：模型读到"自己曾经承诺过按格式来"，后续输出格式会明显更稳定。
这叫"示例对话"（example dialogue），是 few-shot 的对话形态。

### 用途 ③：prefill 抢答引导（进阶，知道即可）
如果消息列表**以 assistant 结尾**且内容是半截话，比如：
```python
messages = [
    {"role": "system", "content": "只输出 JSON"},
    {"role": "user", "content": "提取信息：xxx"},
    {"role": "assistant", "content": "{"},   # 半截！
]
```
模型会接着 `{` 往下写，强制输出以 `{` 开头——治"模型开口先来一句'好的，以下是JSON：'"的毛病。多数 OpenAI 兼容网关支持，但不保证，具体模型要试。

## 4. 常见误区

- ❌ 把 system 当聊天气氛组。它是**全程生效的行为约束**，权限最高
- ❌ 以为 assistant 内容必须是模型真说过的。它可以是你伪造的（用途②③）
- ❌ 以为 server 帮你记历史。记忆 100% 靠你每次全量传，传多少它"记得"多少
- ⚠️ 历史越长 token 越贵、响应越慢——所以工程上要做"历史截断/摘要"
